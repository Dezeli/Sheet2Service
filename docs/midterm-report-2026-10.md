## 1. 요약

현업에서는 업무가 스프레드시트 위에서 운영되는 경우가 많다. 접수 대장, 재고표, 대여 기록, 회원 명부처럼 사람이 상태 컬럼을 손으로 고치며 돌아가는 시트는, 그 시트를 처음 받은 사람이 "이것이 무엇이고, 왜 존재하며, 어떻게 운영되는지"를 파악하는 데 시간이 걸리고, 복잡할수록 더 걸린다.

본 프로젝트는 **범용 스프레드시트를 입력받아 AI가 그 시트의 업무 흐름을 파악하고, 그 이해로부터 실제로 동작하는 운영 서비스(조회·접수·처리·관리 화면)를 자동으로 생성하는 시스템**을 만든다. 핵심은 "AI가 서비스 기능을 고른다"가 아니라 **"AI가 시트를 읽는다"**에 있다. 시트에 대놓고 적혀 있지 않은 업무 흐름(상태 전이, 담당자 배정, 기한, 회신 같은 후속 흐름)을 컬럼과 값의 패턴에서 뽑아내고, 사람이 그 이해를 확인·수정하면, 서비스는 그 이해에서 결정론적으로 따라 나온다.

10월 중순 지도교수 면담에서 1차 버전(미리 만든 기능 템플릿 중 AI가 추천하고 사용자가 고르는 방식)에 대해 "AI가 왜 필요한지 분명하지 않다", "템플릿을 하나하나 미리 만들어야 한다"는 지적을 받았고, 이에 따라 10월 말 **시트 이해를 중심 산출물로 두는 구조로 전환**했다. 현재 다음이 동작한다.

- 결정론적 분석에 **컬럼 간 운영 신호**(조건부 결측, 날짜 채움 순서, 함께 채워지는 컬럼, 수량 관계 등)를 더해 LLM에 사실만 제공
- Claude API 1회 호출로 **시트 이해**(종류·목적·행위자·컬럼 역할 27종·업무 흐름 여러 개·행의 생애·확인 질문)를 JSON Schema로 강제 수신
- 사용자가 이해를 확인·수정하는 화면, 수정은 모델 결과와 분리 저장
- 이해에서 **호출 없이** 서비스 설정을 도출하고, 시트의 컬럼을 직접 바꾸는 행 업무 흐름 실행기와 항목 신청 흐름으로 운영 화면(사용자·관리자·대시보드)을 구성

정답을 아는 평가 시트 15장(운영 시트 10장 + 공공데이터 5장)에 대한 첫 평가에서 시트 종류 15/15, 심어 둔 업무 흐름 20개 전부 탐지(근거 종류 20/20, 선후 관계 19/20), 컬럼 역할 정확도 84~92%(엄격 기준)를 얻었고, 헤더를 약어로 바꾸고 날짜 형식을 섞은 지저분한 판에서도 정확도가 거의 떨어지지 않았다.

## 2. 개요

### 2.1 배경과 문제 정의

- 현업의 많은 운영 업무가 스프레드시트로 수행된다. 시트는 데이터이자 업무 프로세스의 기록이지만, 그 프로세스는 명시되어 있지 않다. `상태`, `담당자`, `접수일`, `처리일`, `회신여부` 같은 컬럼이 "누가 어떤 순서로 무엇을 하는지"를 암묵적으로 담고 있을 뿐이다.
- 시트를 시스템으로 옮기려면 사람이 먼저 그 프로세스를 이해하고 설계해야 한다. 이 이해 비용이 전환의 병목이다.
- 기존 접근(노코드 도구, 템플릿 선택)은 사용자가 이미 자신의 프로세스를 알고 있다고 가정한다. 범용 시트에 대해서는 미리 만든 템플릿으로 모든 경우를 덮을 수 없다.

### 2.2 연구 목표

1. **범용성**: 특정 시트에 맞춘 일회성 서비스가 아니라, 어떤 시트를 넣어도 동작하는 구조.
2. **AI의 역할을 "이해"에 두기**: AI가 시트의 종류·목적·행위자·업무 흐름을 데이터에서 읽어내고, 그 결과를 사람이 검증할 수 있는 형태로 내놓는다.
3. **이해로부터 서비스가 결정론적으로 따라 나오게 하기**: 설계·검증·실행은 코드가 맡아 재현 가능하고 안전하게 한다.
4. **정확도를 측정 가능하게 하기**: 정답을 아는 평가 세트와 채점기로 이해 정확도를 수치화한다.

### 2.3 범위와 전제

- 입력: 현재 CSV 1장(인코딩 자동 판별, 최대 100,000행·500,000셀). XLSX·다중 시트는 진행 예정.
- 출력: 웹 서비스(대시보드·사용자·관리자 화면)와 그 서비스를 돌리는 설정(JSON).
- LLM 호출: 시트당 **이해 1회**만 사용하며, 모든 호출은 사용자의 명시적 승인(버튼 클릭) 뒤에 이루어진다. 기본 파싱·통계·서비스 생성에는 LLM을 쓰지 않는다.
- 사용자: 시트를 올리는 운영 담당자(관리자 역할)와 서비스를 이용하는 요청자(사용자 역할). 인증·권한은 브라우저 세션 범위로 한정(후속 과제).

## 3. 진행 방법

### 3.1 시스템 구조와 기술 구성

| 구성 | 내용 |
| --- | --- |
| 백엔드 | Python 3.14, Django 5.2, Django REST Framework |
| 프론트엔드 | React 19, Vite |
| 데이터베이스 | PostgreSQL 17 |
| 실행 환경 | Docker Compose (db / backend / frontend) |
| LLM | Claude API (claude-sonnet-5), Structured Outputs(JSON Schema 강제), 1회 호출 |

처리 흐름:

```
CSV 업로드
  → 결정론적 분석 (컬럼 통계 + 운영 신호)                 [호출 없음]
  → 시트 이해 (Claude 1회, JSON Schema로 응답 형식 강제)   [호출 1회]
  → 사람이 이해를 확인·수정 (모델 결과와 분리 저장)         [호출 없음]
  → 이해 → 서비스 설정 도출 (결정론)                       [호출 없음]
  → 실행: 사용자 / 관리자 / 대시보드 화면                  [호출 없음]
```

### 3.2 설계 원칙: 결정론과 의미 추론의 분담

- **결정론으로 할 수 있는 것은 결정론으로**: 파싱, 통계, 운영 신호, 설정 검증, 서비스 도출, 상태 전이 실행은 모두 코드다. 재현 가능하고 테스트할 수 있다.
- **LLM에는 의미 추론만**: "이 컬럼은 담당자인가", "이 값 집합은 상태 흐름인가", "이 시트는 왜 존재하는가"처럼 데이터만으로 결정할 수 없는 해석.
- **응답 형식 강제**: LLM 응답은 JSON Schema(enum 중심)로 강제해 형식이 어긋나 비용만 쓰는 경우를 막는다. 공급자의 스키마 복잡도 한도("compiled grammar too large")를 실험으로 확인하고, 컬럼별 항목은 객체 배열 대신 **길이 N의 병렬 배열**, 전이는 `"접수>배정:a1"` 같은 문자열로 인코딩해 한도 안에 두었다. 컬럼 수에 무관함을 14·24·60열 탐침(max_tokens=1)으로 확인했다.
- **지불한 응답은 버리지 않는다**: 검증에 걸린 항목(없는 상태 값, 없는 컬럼 번호, 잘못된 참조)은 응답 전체를 거절하지 않고 그 항목만 낮추거나 제외하며 메모를 남긴다.
- **사람의 수정은 모델 결과와 분리 저장**: 모델 정확도 채점은 원본으로, 서비스 도출은 유효본(원본 + 수정)으로.

### 3.3 운영 신호(Operational Signals)

컬럼별 통계만으로는 업무 흐름을 읽을 수 없다. 행 안에서 컬럼들이 **함께 움직이는 패턴**을 호출 없이 계산해 LLM에 사실로 제공한다(최대 5,000행 표본, 100k행도 동일 비용).

| 신호 | 계산 | 알려 주는 것 |
| --- | --- | --- |
| 값 집합·여부 컬럼 | 고유값 ≤12인 컬럼의 값과 건수, Y/N·O/X 두 값 컬럼 | 상태·분류·여부 후보 |
| 조건부 결측 | 값 집합 컬럼의 값별로 다른 컬럼이 비어 있는 비율 | "처리일은 완료 행에만 있다" → 전이·생애 |
| 채움 사슬·함께 채움 | "B가 있으면 A도 있다", 같은 행에서 함께 채워지는 쌍 | 날짜 사슬 흐름(신청일→승인일→대여일→반납일), 흐름의 관여 컬럼 |
| 흐름 군집 | 위 관계로 얽힌 컬럼 묶음 | 흐름 후보 수 |
| 날짜 선후·간격 | 같은 행의 날짜 순서 비율, 간격 최빈값 | 기한 규칙(접수일+7일) |
| 숫자 관계 | A−B=C, A+B=C, A×B=C | 계산 컬럼(환급액=보증금−공제액, 금액=수량×단가) |
| 식별자·연락처 모양, 자유 글, 함께 비는 조합 | 정규식·고유율·길이 | 역할 후보 |

### 3.4 시트 이해 계약(SheetUnderstanding v1)

LLM은 다음을 고정 어휘 안에서만 답한다.

- `kind`: 대장(register) / 목록(catalog) / 장부(ledger) / 일정 / 명부 / 참조표 / 혼합
- `purpose`, `subject`, `actors`(요청·처리·승인·조회·시스템)
- 컬럼별 `columnRoles`(식별자, 제목, 분류, 상태, 담당자, 요청자 이름, 연락처, 등록일, 기한, 종료일, 시각, 기간, 금액, 수량, 좌표, 이미지, 참조 코드, 결과, 메모, 여부, 계산값 등 27종), `columnConfidence`, `columnEvidence`
- `processes[]`: **여러 개**의 업무 흐름. 각 흐름의 근거 종류(`basis`: 상태 컬럼 / 단계별 날짜 / 여부 컬럼 / 수량 변동 / 의미 추정), 관여 컬럼, 상태와 종류(시작·진행·대기·완료·취소), 전이와 행위자, 확신, 선행 흐름(`after`)
- `lifecycle`(행이 생길 때·바뀔 때·끝날 때), `questions`(서비스 모양이 달라지는 확인 질문)

서버는 상태 값이 실제 데이터에 있는지, 컬럼 번호·흐름 참조가 유효한지 검증하고, 여부 흐름의 대기 상태 보충, 선행 흐름 보충 같은 결정론적 보정을 한다.

### 3.5 이해 → 서비스 설정 도출과 실행기

도출은 코드이며 호출이 없다. 이해를 고치면 즉시 다시 도출된다.

| 이해 | 설정 |
| --- | --- |
| 제목·식별자 역할 | 목록 제목 컬럼 |
| 상태·분류·담당자·여부 역할 | 필터, 차트 |
| 등록일·대상 날짜 | 기본 정렬 |
| 업무 흐름(상태 컬럼) | **행 업무 흐름**: 시트의 상태 컬럼 값을 전이 버튼으로 바꾸고, 담당자·결과 입력, 종료일 자동 기록, 이력 저장 |
| 업무 흐름(단계별 날짜) | 전이 시 해당 단계 날짜에 오늘 기록 |
| 업무 흐름(여부 컬럼) | 시트의 실제 표시값(Y/O)으로 표시하고 동반 컬럼 채움, 선행 흐름 완료 후에만 진행 |
| 대장형 + 요청자 | 사용자 화면의 새 건 접수 폼(흐름이 채우는 컬럼은 제외) |
| 항목형 + 요청자 | **항목 신청 흐름**(신청자·연락처·요청 내용, 접수→승인/거절), 상태 흐름이 있으면 '진행(접수중)' 상태인 항목에만 신청 허용 |
| 제외된 흐름, 확신 낮은 미확인 흐름 | 만들지 않음(메모로 표시) |

실행기는 대장형 시트에서 **행 자체를 건으로** 다룬다. 별도 신청 레코드를 만드는 대신 `ManagedRow`의 해당 컬럼을 직접 바꾸고 `RowHistory`에 변경 이력을 남긴다. 항목형 시트의 신청은 시트 밖 `BlueprintSubmission`에 남는다.

### 3.6 평가 방법

실제 현업 시트를 구할 수 없으므로 **정답을 아는 시트를 만들어** 채점한다.

- 운영 시트 5전형(민원 접수·처리 대장, 장비 대여 대장, 강의실 예약 대장, 비품 입출고 장부, 동호회 회원 명부) × 깨끗한 판/지저분한 판(약어 헤더 `rcpt_dt`·`stat`, 날짜 형식 혼합 `2026.08.24`/`20260824`, 천 단위 쉼표, 값 끝 공백, 빈 컬럼) = 10장. 모든 시트에 흐름 2개 이상, 근거 종류를 섞음.
- 공공데이터 5장(서울 열린데이터광장: 보건소 공지, 상권 영역, 불법주차 IoT 측정, 종로구 관광 정보, 체육시설 예약 정보)을 조회형 대조군으로 포함.
- 정답표: 시트 종류, 컬럼 역할(방어 가능한 대안은 `note|title`처럼 허용), 흐름 목록(근거·관여 컬럼·상태·전이·선후).
- 지표: 종류 정확도, 컬럼 역할 정확도(엄격/대안 허용), 흐름 탐지 수, 흐름 대응(관여 컬럼 겹침으로 짝지음), 근거 종류 일치, 상태·전이 복원, 선후 일치. 모델이 스스로 "확신 낮음"으로 둔 과잉 흐름은 "가능성"으로 따로 센다.

### 4.2 현재 구현 범위

- **입력·분석**: CSV(UTF-8/CP949 자동), 컬럼 통계, 운영 신호(§3.3).
- **시트 이해**: 호출 1회(출력 상한 16k 토큰, 180초), 스키마 강제, 서버 검증·보정, 결과 저장.
- **이해 화면**: AI가 읽은 시트(제목·목적·종류·관련된 사람·행의 생애), 업무 흐름 카드(단계 그림, 근거·전이 접기, 맞아요/제외), 컬럼 역할 표(select로 수정, 확신 낮은 것만 보기), 확인 질문과 답변, "이렇게 서비스가 만들어집니다" 미리보기(사용자·관리자·대시보드), 고정 실행 바.
- **서비스 화면**
  - 사용자: 항목 목록(검색·필터·정렬·상세), 행마다 흐름 상태 배지, 새 건 접수 폼(대장형), 항목 신청하기/신청 불가(항목형), 내 접수·신청 현황과 본인 전이(취소)
  - 관리자: 필드 구성·선택지 관리·데이터 관리(1차 버전 유지), 행 업무 흐름별 메뉴(상태 필터, 담당자·기한 열, 전이 버튼과 입력 모달, 행 이력), 항목 신청 내역(승인·거절)
  - 대시보드: 분류·상태별 건수 차트
- **평가 자산**: 평가 시트 10장 생성 스크립트와 정답표, 공공데이터 정답표 5개, 채점기.
- **테스트**: 백엔드 자동 테스트 159개(운영 신호, 이해 계약, 수정 병합, 도출, 행 흐름 실행, 항목 신청, API), 헤드리스 브라우저로 업로드→이해→적용→접수→처리 흐름 확인.

### 4.3 평가 결과 (2026-10-25, 시트 15장, 호출 15회)

| 묶음 | 시트 종류 | 컬럼 역할(엄격) | 컬럼 역할(대안 허용) | 흐름 탐지 | 근거 종류 | 선후 관계 |
| --- | --- | --- | --- | --- | --- | --- |
| 운영 시트 깨끗 5장 | 5/5 | 85% | 93% | 10/10 | 10/10 | 10/10 |
| 운영 시트 지저분 5장 | 5/5 | 84% | 91% | 10/10 | 10/10 | 9/10 |
| 공공데이터 5장 | 5/5 | 92% | 97% | 흐름 없음 정답 | – | – |

- 심어 둔 업무 흐름 20개를 전부 찾았고 근거 종류도 전부 맞혔다. 과잉 탐지 4개는 모두 모델이 스스로 "확신 낮음"으로 표시해 서비스 도출에서 사용자 확인을 요구하도록 처리된다.
- 지저분한 판에서 거의 떨어지지 않았다. 운영 신호가 헤더 이름에 의존하지 않기 때문이다. "복잡한 시트일수록"에 대한 첫 답이다.
- 역할 오류는 대부분 경계가 모호한 경우(민원내용을 제목으로, 등급을 상태로, 승인일을 대상 날짜로)였다. "대안 허용" 수치는 정답표에 방어 가능한 둘째 답을 허용한 결과이며, 엄격 수치를 보수적 기준으로 함께 기록했다.
- 비용: 시트당 입력 6~14k, 출력 1.6~7.8k 토큰(모델의 사고 토큰 포함), 20~80초. 15회 합계 입력 131k·출력 71k 토큰.

### 4.4 한계와 발견한 문제

- 신청 폼 필드가 고정 3개(신청자·연락처·요청 내용)다. 예약일·시간대·인원 같은 필드를 이해에서 도출하지 못한다.
- 장부형(수량 변동) 흐름은 기록 추가 폼이 필요해 아직 도출에서 제외된다.
- 전이는 스냅샷 데이터에서 직접 관찰할 수 없어 상태별 채움 차이와 의미로 추정한다. 근거가 없는 전이는 확신 낮음으로 표시하지만 완전히 막지는 못한다.
- 모델의 사고(thinking) 토큰이 출력 상한을 함께 소비해 넓은 시트에서 응답이 잘린 사례가 있었다(상한을 8k→16k로 조정).
- 사용자 식별이 브라우저 세션뿐이라 공개 운영 수준의 권한·인증이 없다.
- 1차 버전에서 구현했던 예약 정원·대여 재고 같은 세부 운영 규칙은 아직 이해→도출 경로로 다시 들어오지 않았다.
