# 시트 이해 (설계안)

## 목적

이 프로젝트의 주제는 "현업의 복잡한 스프레드시트를 실제 운영 시스템으로 바꾸기"다. 사람이 낯선 시트를 받으면 그것이 **무엇이고, 왜 존재하며, 어떻게 운영되는지** 알아내는 데 시간이 걸린다. 복잡할수록 더 걸린다. AI의 역할은 그 이해를 대신 하고, 이해가 맞으면 서비스는 거기서 따라 나오게 하는 것이다.

지금 파이프라인은 `분석(통계) → 서비스 설정 → 실행`이라 이해가 Claude 안에만 잠깐 있다가 사라진다. 사람은 결과 화면만 보므로 AI가 무엇을 알아냈는지 볼 수 없고, "체크박스로 골라도 같지 않냐"는 물음에 답이 없었다. 바꾼 파이프라인은 다음과 같다.

```
분석(결정론적 통계 + 운영 신호) → 시트 이해(Claude, 스키마 강제) → 사람 확인·수정 → 서비스 설정(결정론적 도출) → 실행
```

"시트 이해"는 저장되고, 화면에 보이고, 고칠 수 있고, 채점할 수 있는 **산출물**이다. 서비스 설정은 이해에서 도출되므로 이해를 고치면 서비스가 따라 바뀐다. 채팅의 대상은 "기능"이 아니라 "이해"가 된다.

## 역할 분담

| 단계 | 담당 |
| --- | --- |
| 컬럼 통계, 값 집합, 날짜 순서, 조건부 결측 같은 운영 신호 계산 | 서버 (호출 없음) |
| 시트의 종류·목적·행위자·컬럼 역할·업무 흐름·행의 생애·열린 질문을 스키마에 맞춰 답함 | Claude (호출 1회) |
| 이해 검증(컬럼 번호·상태 값이 실제 데이터에 있는지), 저장, 화면 표시 | 서버 |
| 이해 확인·수정("이 컬럼은 담당자가 아니라 접수자") | 사용자 |
| 이해 → 서비스 설정 도출 | 서버 (호출 없음) |

원칙은 기존과 같다. 결정론으로 할 수 있는 것은 결정론으로, 의미 추론만 Claude에게, 응답 형식은 JSON Schema로 강제하고 문법이 싼 인코딩을 쓴다.

## 이해 산출물 (`SheetUnderstanding` v1)

컬럼 수 N인 시트에 대해 다음을 반환한다. 컬럼별 항목은 객체 배열 대신 **길이 N의 병렬 배열**로 받는다(공급자 문법 한도 대응, `catalog.labels`와 같은 방식).

```json
{

  "kind": "register",
  "subject": "주민 민원",
  "purpose": "주민 민원을 접수해 담당 부서에 배정하고 처리 결과를 회신하기 위한 대장",
  "actors": [
    {"id": "a1", "label": "접수 담당자", "kind": "handler"},

    {"about": "column", "column": 9, "text": "처리기한은 접수일 기준 7일 규칙인가요?"}
```

### 허용 값

| 항목 | enum |
| --- | --- |
| `kind` | `register` 행=사건·건, 상태가 바뀜(대장·접수부·진행표) · `catalog` 행=항목, 거의 변하지 않음(목록·안내) · `ledger` 행=거래 기록, 추가만 됨(장부·일지) · `schedule` 행=일정 · `roster` 행=사람·조직(명부) · `reference` 코드표·참조표 · `mixed` |
| `actors[].kind` | `requester` 요청하는 사람 · `handler` 처리하는 사람 · `approver` 승인하는 사람 · `viewer` 보기만 함 · `system` |
| `columnRoles[]` | `identifier` · `title` · `category` · `status` · `owner`(담당자) · `actor_name`(요청자·신청자 이름) · `contact` · `date_created` · `date_updated` · `date_due` · `date_event` · `date_closed` · `time`(시각) · `duration`(기간·일수) · `amount` · `quantity` · `number`(그 밖의 측정값) · `location` · `coordinate` · `url` · `image` · `reference_code` · `result` · `note` · `flag` · `derived`(계산값) · `unknown` |
| `columnConfidence[]` | `high` · `medium` · `low` |
| `states[].kind` | `start` · `active` · `waiting` · `done` · `cancelled` |
| `processes[].confidence` | `high` · `medium` · `low` — 전이가 `conditional_missing` 같은 데이터 근거 없이 상태 이름만으로 적혔으면 `low` |
| `processes[].basis` | `status_column` 상태 값 컬럼이 있음 · `milestone_dates` 단계별 날짜 컬럼이 차례로 채워짐(접수일→배정일→완료일) · `flag_and_dates` 여부 컬럼(Y/N·O/X)과 그때 채워지는 컬럼 · `amount_balance` 금액·수량이 누적되거나 차감됨(입금·잔액, 입고·출고) · `inferred` 위 근거 없이 컬럼 의미만으로 추정 |
| `questions[].about` | `purpose` · `column` · `process` |

### 업무 흐름은 여러 개이고, 대놓고 적혀 있지 않다

시트에는 "이 시트의 흐름은 이렇다"가 적혀 있지 않다. 흐름은 컬럼과 값의 패턴에서 **뽑아내야** 하고, 한 시트에 **여러 흐름**이 겹쳐 있는 것이 보통이다. 민원 대장에는 처리 흐름과 회신 흐름이, 장비 대여 대장에는 대여 흐름과 점검 흐름이, 회원 명부에는 가입 흐름과 회비 납부 흐름이 같이 있다. 그래서 `processes`는 배열이고, 각 흐름은 자기 근거(`basis`)와 관여 컬럼(`columns`)을 밝힌다.

흐름의 근거는 상태 컬럼만이 아니다. 상태 컬럼이 없어도 날짜 컬럼이 순서대로 채워지면(`milestone_dates`) 그것이 상태 기계이고, `완료여부` 같은 여부 컬럼과 그때 함께 채워지는 컬럼이 있으면(`flag_and_dates`) 두 상태짜리 흐름이며, 입금·잔액처럼 수량이 움직이면(`amount_balance`) 장부 흐름이다. 흐름 사이의 관계는 `after`(p1이 끝나야 p2가 시작)로 적고, 없으면 독립이다. 모델이 비워 두면 서버가 `fill_chain`으로 보충한다(그 흐름의 진행 컬럼이 전부 다른 흐름의 컬럼 뒤에 채워질 때).

`transitions`는 `"<from>><to>:<actorId>"` 문자열이다. `processes`가 비어 있으면 "흐름 없음"(`catalog`·`reference` 시트)이다. `basis = status_column`이면 `columns[0]`이 상태 컬럼이고 `states[].value`는 실제 데이터에 있는 값이어야 하며 서버가 검증한다. `milestone_dates`면 `columns`가 순서대로 단계 날짜 컬럼이고 상태는 "마지막으로 채워진 날짜"로 정의된다. 길이 N 배열의 길이가 다르거나 없는 컬럼·행위자를 가리키면 해당 항목만 `unknown`·빈 값으로 내리고 응답은 버리지 않는다(지불한 응답을 형식 때문에 날리지 않는다).

### 열린 질문

확신이 낮아 이해가 갈리는 지점만 `questions`에 쓴다. 확인 화면에서 사용자가 답하면 이해에 반영되고, 답이 없어도 서비스 도출은 진행된다(확신 `low`인 역할은 보조 정보로만 쓴다).

## 운영 신호 (결정론적 사전 계산)

현재 분석은 컬럼별 형식·고유값 수·결측률·예시 행을 준다. 업무 흐름을 읽으려면 **행 안에서 컬럼들이 함께 움직이는 패턴**이 필요하다. 호출 없이 계산해 프롬프트에 `<operational_signals>`로 넣는다.

| 신호 | 계산 | 알려 주는 것 |
| --- | --- | --- |
| 값 집합 | 고유값 ≤ 12인 문자 컬럼의 값과 건수 | 상태·분류 후보와 상태 집합 |
| 여부 컬럼 | 값이 Y/N·O/X·예/아니오·완료/미완료 두 가지인 컬럼 | `flag_and_dates` 흐름 후보 |
| 조건부 결측 | 값 집합·여부 컬럼 A의 값별로 다른 컬럼 B의 결측률 | "처리일은 완료 행에만 있다" → 생애·전이, 흐름의 관여 컬럼 |
| 날짜 채움 사슬 | 날짜 컬럼들 사이에서 "B가 있으면 A도 있다"가 성립하는 순서 | `milestone_dates` 흐름(접수일→배정일→완료일)과 단계 수 |
| 날짜 순서 | 날짜 컬럼 쌍마다 같은 행에서 앞서는 비율 | 접수일 → 처리일 순서, 기한 |
| 날짜 간격 | 두 날짜 컬럼의 차이 분포(최빈값) | 기한 규칙(접수일+7일) |
| 수량 움직임 | 숫자 컬럼 쌍의 합·차 관계(입고−출고=재고), 행 순서에 따른 누적 | `amount_balance` 흐름 |
| 흐름 군집 | 조건부 결측·채움 사슬로 함께 움직이는 컬럼 묶음 | 흐름이 몇 개인지, 각 흐름의 관여 컬럼 |
| 식별자 | 고유율 ≈ 1, 일정한 패턴·연번 | identifier |
| 연락처·주소·URL | 정규식 비율 | contact·location·url |
| 채움 패턴 | 행별 결측 컬럼 조합 상위 5개 | "뒤쪽 컬럼은 처리 후에 채운다" |
| 자유 글 | 평균 길이, 고유율 | note·result |

신호는 사실만 제공한다. 해석(어느 것이 상태인지, 누가 바꾸는지)은 Claude가 한다.

## 이해 → 서비스 설정 도출

도출은 서버가 결정론적으로 한다. 호출이 없으므로 이해를 고치면 즉시 다시 도출한다.

| 이해 | 설정 |
| --- | --- |
| `identifier`·`title` | `catalog.titleColumn`(title 우선, 없으면 identifier) |
| `category`·`status`·`owner` | `catalog.filterColumns`, `charts` |
| `note`·`result`·`title`·`actor_name` | `catalog.searchColumns` |
| `date_created` | `catalog.sort` 최신순 |
| `processes[]` 각각 | **행 운영 흐름** 하나씩(`rowWorkflow`). `status_column`은 상태 컬럼이 상태 기계, `milestone_dates`는 단계 날짜가 상태(전이 시 해당 날짜 자동 기록), `flag_and_dates`는 두 상태와 함께 채울 컬럼, `amount_balance`는 입력 폼 + 잔액 집계. 전이는 행위자별 버튼, `owner` 컬럼은 배정 입력, `date_closed`는 `done` 전이 시 자동 기록, `date_due`는 기한 표시·지남 강조. `after`가 있으면 선행 흐름이 `done`일 때만 버튼 활성 |
| `kind = register`, `rowCreated`가 `requester` | 사용자 화면에 "새 건 접수" 폼(컬럼 역할에서 입력 필드 도출: actor_name·contact·category·note) |
| `kind = catalog` | 조회 중심. 신청·문의는 이해에 근거가 있을 때만(예: `date_event`+`quantity` → 예약 흐름 후보) |
| `kind = ledger` | 추가 전용 입력 + 기간·합계 집계 |
| `kind = reference` | 다른 시트의 선택지로만 사용(다중 시트 단계) |
| `actors` | 역할 화면 수. `requester`가 있으면 사용자 화면, `handler/approver`는 관리자 화면 |

### 계약에 필요한 확장

현재 조합형 계약의 워크플로는 **CSV 밖에 새 신청을 만드는** 구조다(`submission`). 대장형 시트는 **행 자체가 건**이고 상태가 행의 컬럼에 있다. 계약에 `rowWorkflow`를 추가한다.

```json
{"id": "flow_1", "title": "민원 처리", "statusColumn": 7, "ownerColumn": 8, "dueColumn": 9, "closedColumn": 10,
 "states": [...], "initialState": "접수", "transitions": [{"from": "접수", "to": "배정", "actor": "admin", "sets": ["owner"]}],
 "createForm": {"actor": "user", "columns": [3, 4, 5, 6]}}
```

실행기는 `ManagedRow.values`의 상태 컬럼을 바꾸고 이력을 남긴다. 기존 `submission` 워크플로는 `catalog` 시트용으로 그대로 둔다. 10-11 템플릿에 있던 정원·재고·금액은 이 틀에서 `quantity`·`amount`·`date_event` 역할의 조합으로 다시 들어오며, 이해가 그 근거를 제공할 때만 도출한다.

## 화면

1. 업로드 → 분석 → **이해 확인 화면**(새로 추가). 한 장에 "이 시트는 …이고 …를 위해 존재합니다", 행위자, 컬럼 역할 표(역할·확신·근거), 상태 흐름 그림, 행의 생애, 열린 질문.
2. 사용자는 역할·상태 종류·전이를 고치고 질문에 답한다. 수정은 `understanding_overrides`로 저장되어 원 응답과 구분된다(채점에 쓴다).
3. "서비스 만들기" → 도출 → 기존 대시보드·사용자·관리자 화면.
4. 서비스 화면의 채팅은 이해를 고치는 입구가 된다("처리기한은 접수일+5일이야"). 기능 요청 채팅과 자율 부품은 보조 경로로 남긴다.

## 평가

실제 현업 시트는 구할 수 없으므로 **정답을 아는 시트를 만든다**. 전형 4종(접수·처리 대장, 재고·자산, 예약·일정, 회원·고객)을 각각 깨끗한 판과 지저분한 판(병합 헤더, 메모 행, 코드값, 빈 컬럼, 섞인 날짜 형식)으로 만들고 정답표(`*.truth.json`: kind, 컬럼 역할, 흐름 목록과 각 흐름의 basis·관여 컬럼·상태 집합·전이·관계)를 함께 둔다. 전형마다 흐름을 **둘 이상** 넣고 근거 종류를 섞는다(예: 접수·처리 대장 = 상태 컬럼 흐름 + 여부 컬럼 회신 흐름, 재고·자산 = 수량 흐름 + 날짜 사슬 점검 흐름). 흐름이 하나뿐인 시트만으로 채점하면 "여러 흐름을 알아보는가"를 재지 못한다. 기존 공공데이터 샘플 5종은 `catalog` 정답으로 포함한다(범용이면 조회형도 들어와야 한다).

| 지표 | 계산 |
| --- | --- |
| 컬럼 역할 정확도 | 정답과 일치한 컬럼 수 / N |
| 흐름 개수 | 정답 흐름 수 대비 탐지 수(누락·과잉 각각) |
| 흐름 대응 | 관여 컬럼 집합의 겹침으로 정답 흐름과 짝을 지은 뒤, 짝지어진 비율 |
| 근거 종류 | 짝지어진 흐름의 `basis` 일치 |
| 상태 집합 복원 | 흐름별 정답 states와의 집합 일치율 |
| 전이 복원 | 흐름별 정답 transitions와의 일치율(행위자 포함·제외 각각) |
| 흐름 관계 | `after` 관계 일치 |
| 종류 정확도 | `kind` 일치 |
| 목적 적절성 | 사람이 1~3점 |

시트당 호출 1회. 지저분한 판에서 깨끗한 판 대비 얼마나 떨어지는지가 "복잡한 시트일수록"에 대한 답이 된다. 정답표의 역할은 방어 가능한 대안을 `note|title`처럼 적을 수 있고, 모델이 `confidence: low`로 둔 과잉 흐름은 "가능성"으로 따로 센다.

### 2026-10-25 첫 라운드 (15장, 15회)

| 묶음 | 종류 | 역할(엄격) | 역할(대안 허용) | 흐름 탐지 | 근거 | 선후 |
| --- | --- | --- | --- | --- | --- | --- |
| 운영 시트 깨끗 5장 | 5/5 | 85% | 93% | 10/10 | 10/10 | 10/10 |
| 운영 시트 지저분 5장 | 5/5 | 84% | 91% | 10/10 | 10/10 | 9/10 |
| 공공데이터 5장 | 5/5 | 92% | 97% | 흐름 없음 정답, 가능성 2 | - | - |

지저분한 판(약어 헤더, 날짜 형식 혼합, 천 단위 쉼표, 끝 공백, 빈 컬럼)에서 거의 떨어지지 않았다. 운영 신호가 헤더 이름에 의존하지 않기 때문이다. 과잉 흐름 4개는 전부 모델이 스스로 낮은 확신으로 표시했다.
