# 부품 계보와 화면 조립

## 목표와 이번 증분

사용자 요청을 받을 때 기존 부품의 설정 변경·조합·확장을 먼저 검토한다. 기존 기능으로 표현할 수 없는 동작이 확인될 때에만 새 부품 후보를 만든다. 부품은 계열과 버전, 부모 버전으로 계보를 기록한다. **최신 버전이 항상 우선하지는 않는다.** 요구를 충족하는 가장 단순한 검증된 버전을 선택한다.

첫 증분은 이미 실행 중인 기능 7개의 계약을 PostgreSQL에 등록한다. `ComponentVersion`은 부품의 계보, 기능, 적용 화면, 저장소 코드에 연결되는 구현 키, 상태를 저장한다. 실행 코드나 사용자 CSV 데이터는 DB에 저장하지 않는다. 두 번째 증분에서는 [`component_matching.py`](../backend/uploads/component_matching.py)에 결정적 후보 검색과 `ComponentMatch` 판단 기록을 추가했다. 세 번째 증분은 [`component_planning.py`](../backend/uploads/component_planning.py)와 [`claude_api_settings`](../backend/claude_api_settings/README.md)에 부품 판단 계약을 정의했다. 네 번째 증분에서 **기존 서비스 수정 호출 한 번**에 이 판단을 연결했다. 서비스 생성과 Preview 실행 경로는 그대로이며, 아직 새 부품을 자동 생성하거나 실행하지 않는다.

## 초기 등록부

| 부품 계열 v1 | 화면 | 실제 제공하는 기능 |
| --- | --- | --- |
| `catalog-browser` | 사용자 | CSV 항목 목록·상세 |
| `text-search` | 사용자 | 지정된 컬럼 텍스트 검색 |
| `exact-filter` | 사용자 | 지정된 컬럼의 값 일치 필터 |
| `count-chart` | 대시보드 | 컬럼별 전체 항목 수 집계 |
| `submission-form` | 사용자 | 항목별 입력값 검증·신청 저장 |
| `submission-status` | 사용자·관리자 | 본인/전체 신청 조회·허용 상태 전환 |
| `catalog-management` | 관리자 | 데이터 행·필드명·선택지 관리 |

이들은 현재 조합형 실행기와 기존 관리자 화면에서 확인 가능한 동작만 나타낸다. `예약 신청`이라는 표시 제목은 시간 슬롯·정원·중복 예약 검증을 제공한다는 근거가 아니다. 로그인·권한 계정, 실제 예약, 결제, 지도도 초기 부품에 등록하지 않는다. 기존 큰 업무 템플릿은 참고 구현으로 남기되, 작은 범용 부품으로 검증되기 전에는 공용 후보로 광고하지 않는다.

등록된 구현 키와 주장 가능한 기능·화면의 정확한 대응은 [`component_contract.py`](../backend/uploads/component_contract.py)에 둔다. DB 행이 임의로 기능을 주장해도 `ComponentVersion.clean()`이 거절한다. 새 버전의 부모는 같은 계열의 낮은 버전이어야 한다. 이 계약은 **메타데이터 검증**이며, 새 구현을 실제로 실행 가능하게 만드는 단계는 아니다.

## 다음 증분의 선택 절차

1. 사용자 요청을 `필요한 동작`, `대상 화면`, `데이터 조건`으로 해석한다. Claude가 의미를 해석하고 서버가 입력 형식을 검증한다.
2. 서버가 등록부에서 대상 화면과 필수 기능을 만족할 수 있는 후보를 찾는다. 기능 상한이나 필수 조건이 맞지 않는 후보를 결정적으로 제외한다.
3. 설정만 바꾸면 되는지, 다른 부품과 조합하면 되는지 검사한다. 후보의 사용 횟수보다 요구와의 적합성 및 검증 근거를 우선한다.
4. 부족한 동작이 있으면 가장 가까운 계보 버전의 확장을 검토한다. 새 부품 생성은 `기존 후보로 불가능한 동작`과 재현 가능한 검사 사례를 기록한 뒤 허용한다. 비슷한 후보가 있으면 그 후보를 쓸 수 없는 이유를 남긴다.
5. 생성 후보는 격리된 개발 환경에서 빌드·검사하고 기존 버전의 사용 사례도 확인한다. 통과한 버전만 등록한다. 모델 응답은 `reuse`, `compose`, `extend`, `create` 등의 enum 결정과 후보 ID·기능 차이·근거를 갖는다. 실제 프롬프트와 JSON Schema는 이 단계에서 `claude_api_settings`에 별도 파일로 둔다.

현재 구현한 검색은 화면과 기능 키를 받아 사용 가능한 부품 버전만 비교한다. 한 계열에서는 버전 하나만 선택하며, 같은 요구를 충족하면 부품 수·불필요한 기능 수·버전 순으로 단순한 조합을 우선한다. 결과는 `reuse`, `compose`, `gap` enum과 선택한 부품 키, 부족한 기능, 비슷한 후보의 탈락 이유(`not_available`, `wrong_surface`, `missing_capabilities`, `alternative_version`)를 포함한다. `gap`은 **새 부품 생성 결정이 아니다.** 이후 Claude가 재사용 가능한 설정 변경이나 기존 버전의 확장 가능성을 검토할 입력이다. 새 기능 이름도 `account.login` 같은 데이터 키로 받되, 등록되지 않은 기능은 실행할 수 있는 것으로 취급하지 않는다. 판단 기록에는 기능 키와 결과만 저장하고 자연어 요청과 CSV 값은 저장하지 않는다.

세 번째 증분의 응답은 요구별 `surface`·`knownCapabilities`·`newRequirement`와 `reuse/compose/extend/create/needs_input` 결정을 담는다. 실행 가능한 부품 키는 등록부의 `available` 항목에서만 선택할 수 있다. 서버는 `reuse/compose`가 검색 결과와 일치하는지, `extend`에 같은 화면의 관련 부품이 있는지, `create`에 미충족 기능과 후보 배제 근거가 있는지 검사한다. enum에 등록한 로그인·지도·예약 기능은 **미구현 요구 어휘**이며 선택 가능한 부품이 아니다. 자연어 `reason`의 진위와 새 코드의 품질은 이 검사만으로 증명되지 않는다. 새 부품 생성·검증·승격은 후속 단계다.

다섯 번째 증분은 `unsupported` 수정 응답의 `extend/create` 계획을 `ComponentCandidate`에 모은다. 화면·기능 enum·미등록 요구·판단 종류·기준 부품·차단 사유의 정확한 조합으로 중복을 묶고, 반복 횟수와 최근 후보 검색 기록을 보존한다. 자연어 요청 전체와 CSV 원본은 후보 행에 저장하지 않는다. 미등록 요구와 모델의 짧은 근거는 후보의 명세 초안으로 저장하므로 이후 생성 단계에서 별도 검증이 필요하다. **후보는 실행 가능 부품이 아니다.** 등록부 `available` 조회에는 포함되지 않는다. 표현이 다른 유사 요구를 의미상 합치는 일은 아직 하지 않는다.

여섯 번째 증분의 `related_component_candidates()`는 같은 화면의 열린 후보를 기능 겹침·기준 부품 버전·계열로 정렬한다. 기능 enum이 없는 새 요구는 공백과 대소문자를 정리한 문구가 같을 때만 관련 후보로 반환한다. 결과는 후보 ID와 `same_requirement`·`same_base_version`·`same_lineage`·`same_capabilities`·`shared_capabilities` 근거를 포함하며, 다른 사용자의 요구 문구를 반환하지 않는다. 유사성은 재사용 검토의 입력일 뿐 자동 병합·공용 승격 근거가 아니다. 아직 Claude 요청과 자동 생성 경로에는 연결하지 않았다.

일곱 번째 증분에서는 미구현 후보에 대해 사용자가 앱의 명시적인 버튼을 누르면 Claude 호출 **한 번**으로 역할별 소스 초안을 만든다. 별도 사전 안내는 기능·미등록 요구·해당 업로드의 짧은 판단 근거·관련 후보 메타데이터를 전송한다고 밝힌다. 원본 CSV나 다른 업로드의 자유 문구는 전송하지 않는다. `ComponentDraft`는 생성 소스와 호출 기록을 DB에 보관한다. 서버는 응답 구조·크기·기능 주장·Python 구문을 검사하지만 소스를 불러오거나 실행하지 않는다. 이 초안이 통과해도 실제 동작·보안·디자인은 검증된 상태가 아니며 `ComponentVersion.available`에는 들어가지 않는다.

`ComponentVersion.status`는 `draft → validated → available → deprecated` 단계다. `available`은 등록된 구현이 현재 코드에 존재한다는 뜻이고, 임의 생성 코드의 안전성을 자동 보증한다는 뜻은 아니다. 새 버전이 기존 버전을 덮어쓰지 않도록 서비스는 추후 선택한 버전 ID를 고정해 저장한다. 이용 횟수·실패 이력·검증 환경의 다양성은 별도 실행 기록으로 쌓으며 단순 호출 횟수만으로 공용 승격하지 않는다.

## 화면 구성과 디자인

탭은 **원자 부품 하나마다** 만들지 않고 사용자가 이해하는 기능 단위로 묶는다. 예를 들어 `카탈로그` 탭 안에 목록·검색·필터·상세를 조합하고, `예약 신청`과 `이용 문의`는 각자의 탭에서 신청 폼과 내역을 보여준다. 관리자에는 기존 필드 구성·선택지 관리·데이터 관리 메뉴와 업무별 관리 탭을 유지한다. 대시보드는 별도 역할 화면으로 둔다. 제목과 탭 순서는 검증된 서비스 설정으로 결정한다.

각 기능 탭은 자신의 설정·상태·API만 사용한다. 다른 탭의 React 컴포넌트 내부 상태를 직접 읽지 않는다. 공통 데이터 변경은 서버 API와 명시적인 새로고침 경계로 반영한다. 공통 `ServiceDialog`, 목록 검색·표·상태 배지, 역할별 색상과 간격을 재사용해 부품이 늘어도 한 서비스처럼 보이게 한다. 새 부품의 스타일은 해당 탭 범위로 제한하고, 전역 CSS를 바꾸는 방식으로 다른 탭의 디자인을 덮어쓰지 않는다.

로그인·권한처럼 모든 탭에 적용되는 기능은 개별 탭 부품이 아니라 플랫폼 계층의 기능이다. 이를 계보에 등록하더라도 계정·세션·권한의 서버 검사가 준비되기 전에는 `available`로 승격할 수 없다.

## 단계별 구현

1. **완료:** 실제 구현된 부품만 DB에 등록하고 계보·기능 계약을 검증한다.
2. **완료:** 등록부를 읽는 결정적 후보 검색과 `reuse/compose/gap` 판단 기록을 구현한다.
3. **완료:** 기존 서비스 수정 호출에 enum 응답 계약·프롬프트·로컬 검증을 연결한다. 미구현 기능은 계획만 반환하고 기존 설정을 유지한다.
4. **완료:** 미구현 기능 후보를 중복 없이 저장하고 확장할 기준 버전을 연결한다.
5. **완료:** 기능과 계보를 기준으로 관련 후보를 로컬에서 찾는다. 자동 병합은 하지 않는다.
6. **현재 단계:** 사용자 승인 후 미구현 부품의 소스 초안을 생성해 DB에 보관한다. 초안은 실행하지 않는다.
7. 기능 탭 호스트를 도입하고 선택된 부품 버전을 서비스 설정에 고정한다. 사용자·관리자 화면의 기존 스타일을 기준으로 탭별 결합을 줄인다.
8. 새 부품 후보의 격리 검증·승격 절차를 구현한다. 로그인 같은 플랫폼 기능은 별도의 권한/보안 검사 기준을 충족한 뒤 연결한다.

현재 저장소 규칙상 에이전트가 사용자 키로 Claude를 호출하려면 호출마다 별도 승인이 필요하고, 코드 커밋에도 변경 내용과 메시지에 대한 승인이 필요하다. 이 후보 검색 증분은 Claude를 호출하지 않는다.
